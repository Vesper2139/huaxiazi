# 盲评评测证据受控接收规程

版本：1.0
状态：操作规程草案；尚无真实数据或受控核验结果。
用途：为阶段 0 评测准入收集授权与独立盲评证据，补足 JSON 样本审计器无法证明的外部事实。

## 1. 信任边界

`blind-validate`、评分器和清单校验器能够检查样本字段、双评标签结构、PII 启发式、样本配额、哈希和记录间隔离。它们不能证明来源授权真实、评审者身份真实、评审者互相独立、评审者没有看到其他答案，或提交时间来自可信时钟。

因此将准入证据分为三层，报告中不得合并成一个 `valid=true`：

1. **记录完整性**：由项目工具自动校验，针对确定的数据快照和准入协议。
2. **授权与用途**：由指定数据保管人检查授权/许可原件及评测用途、脱敏、保留期是否匹配。
3. **评审独立性**：由与标注和候选模型运行分离的评测保管人，检查评审者身份映射、单独分发、原始提交、提交时间、盲包版本和利益冲突声明。

数据包中的 `reviewer_id`、`verification_status`、时间字符串或哈希都是待核验声明。未对照受控原始材料时，状态必须是 `not_verified`。不应将姓名、邮箱、证件、授权原件或身份映射写入 Git 工作区、盲评 JSONL、候选运行清单或普通日志。

## 2. 职责隔离

- **数据来源负责人**登记来源、权利基础和允许用途；不得替代评审独立性核验。
- **评测保管人**管理密封身份映射与原始提交证据，并核验评审独立性；除为争议裁定所需外，不参与样本内容金标制作。
- **评审协调人**生成并分发随机盲包；不能向评审者披露候选模型/运行身份、其他评审答案或 gold。
- **评审者**各自独立提交完整标签；不可通过共享文件覆盖他人答卷。
- **模型运行人**只拿到冻结输入快照，不拿到答案、评审身份或 sealed alias 映射。
- **审计复核人**核对密封材料、证据清单和数据哈希；可与评测保管人不同。

同一自然人可以承担多个行政角色，但不能核验自己生成的授权或评审证据。团队无法做到完全职责分离时，应记录冲突并由第二名独立复核者补位；没有补位则证据状态保持 `not_verified`，不得通过阶段门槛。

## 3. 接收流程

### 3.1 登记数据来源和用途

1. 为每个来源分配不含个人信息的 `source_ref`。使用 `datasets/ai-evaluation/source-register.template.json` 按 `source-register.schema.json` 登记来源类型、权利基础（自有创作/明确授权/许可条款）、允许用途、授权生效与到期时间、撤回/删除联系人角色、脱敏复核结果和受控证据引用。数据 JSONL 的 `source.license_or_consent_ref` 填对应的 `source_ref`；若样本提供 `source_record_hash`，登记中的可选 `source_record_sha256` 必须与之匹配。`evidence.sha256` 单独绑定授权证据材料，二者不能互换。Schema 通过只证明记录格式正确；占位模板不能作为已登记来源。
2. 原始授权材料进入访问受控的证据库；本仓库只记录不可猜测的 vault artifact 引用和内容 SHA-256。引用不可直接解析为公开 URL 或本地绝对路径。
3. 明确评测用途、评测人员、可见字段、保存期限和删除方式。权利范围不覆盖模型评测、候选输出或必要的受控评审时，不接收该来源。
4. 由数据来源负责人提交登记，再由另一名复核人对照原文核验；登记状态只有在复核完成后才允许改成 `verified`。授权用途必须覆盖候选推理和人工评审；允许训练须单独、明确登记，不得由“可用于评测”推定。

### 3.2 生成盲评任务和独立提交

1. 先按 `datasets/ai-evaluation/dataset-freeze-policy-v1.0.md` 完成精确重复、语义族隔离和 family 级 split，再冻结输入样本快照、`blind-eval.schema.json`、标注手册及去重/冻结规则的版本和 SHA-256，以及随机盲包标识；盲包中不带候选身份、输出、gold 或其他评审答卷。规则版本变更后不得沿用旧 hash。
2. 为每条样本/每名评审生成不同的一次性任务引用。评审者身份映射单独密封保存，只记录随机 `reviewer_ref`。
3. 两位评审在隔离的提交入口各自提交原始完整标签。保存源系统不可变提交 ID、可信接收时间、提交后包哈希及对应盲包哈希。导出的评分标签必须可由这些原始提交重建。
4. 独立性核验检查两位评审确为不同受控身份、任务分开分发、无相互可见权限/共用账号、提交顺序和审计日志没有先看到对方答案的迹象，并取得无协同/利益冲突声明。
5. 两人标签不一致时，第三人使用独立裁定任务；裁定人不得收到候选身份或不必要的原始身份信息。保存裁定原始提交并验证 gold 等于裁定标签。
6. 身份映射与内容评测材料分库存放。普通审计包只引用身份库条目，不携带可识别信息。

### 3.3 冻结与清单封存

1. 定稿 JSONL 后冻结字节内容，计算完整 SHA-256。检查来源/授权证据覆盖每条记录，评审提交覆盖每条记录，且任务/盲包/schema/指南版本一一对应。
2. 在项目目录外的受控位置保存授权证据、原始评审提交、盲包分发日志、身份映射、复核签字和对应哈希；备份也受访问控制和保留期约束。
3. 使用 `datasets/ai-evaluation/evidence-manifest.template.json` 生成清单副本；填入所有条目引用和哈希后，以只读方式封存。不得把仍含占位值的模板当作已核验清单。
4. 使用 `source-register-validate --register source-register.json --dataset blind-eval.jsonl` 核对登记字段、逐样本来源引用、来源类型、用途声明和复核记录；需要文件报告时增加 `--output <new-report.json>`。退出码 0 只表示记录完整且内部引用匹配；`rights_reviewed`、`external_evidence_authenticity_verified_by_tool` 与 `phase_0_gate_passed` 固定为 false。
5. 使用 `blind-evidence-validate --input blind-eval.jsonl --manifest evidence-manifest.json --training canonical.jsonl` 交叉核对证据索引与冻结数据、评审引用和包哈希；校验器要求所有样本的 `reviewer_ref`（及存在时的 `adjudicator_ref`）在整个数据集中全局唯一，以落实每任务一次性引用。需要文件报告时增加 `--output <new-report.json>`。该命令仅校验索引结构与记录一致性；退出码 0 不等于外部证据已验证。
6. 另行运行 `blind-validate` 取得完整数据准入报告；人工复核人与清单摘要一起签署阶段准入记录。评测运行 manifest 仍绑定数据/提示/预测哈希，但不暴露身份映射或授权原件。

只有 `exceptions` 全部不存在 `open` 或 `rejected` 状态时，证据清单才可标记为 `reviewed`；例外处理结论需保留在清单及受控证据引用中。`withdrawn` 条目用于保留已撤回事项的历史；对应数据快照是否仍满足授权范围，必须基于新的快照哈希重新审查，不能只靠异常状态字段判断。

## 4. `verified` 状态的证据标准

只有同时满足以下条件，授权状态或评审独立性状态才能由 `not_verified` 转为 `verified`：

- 有授权保管库中的原始证据引用与 SHA-256，另一名复核者对照原文检查过权利人/权利基础、用途范围和有效期。
- 对应评测输入快照哈希与授权来源登记可追溯；授权范围覆盖本计划中的评测活动。
- 每条记录有两份不同受控评审账户提交，提交内容/盲包 hash/时间均可在原始系统审计记录中复查；争议样本另有独立裁定原件。
- 独立性核验角色不同于相关评审者和候选生成/评分人员；复核记录包含核验日期、角色引用、所查证据引用、结论和例外。
- 原始证据与公开/项目数据包分离，访问者最小化；拒绝、撤回、过期或缺材料时状态为 `rejected` 或 `not_verified`，并说明原因。

清单状态是受控人员作出的审计结论，不是密码学证明。需要抵抗事后篡改时，应在受控审计系统中对最终清单摘要签名并保留签名公钥/证书链；在签名验证能力落地前，不要宣称 JSON 中的 SHA-256/状态字段已证明来源真实性。

## 5. 个人信息与撤回

- 评测集仅保留执行任务所需的脱敏文本和非识别性来源引用；来源登记的 `method_summary` 只写方法级摘要，不写样本、姓名、联系信息或原始授权材料。`blind-validate` 与来源登记校验器会对相关内容字段复用 PII/密钥启发式筛查。自动检测只是筛查，必须人工复核；未通过时拒收或回到来源方修订。
- 身份映射、原始答卷和访问日志必须设置明确访问角色、留存期限、备份过期策略和删除流程。
- 授权撤回/到期时，暂停相关数据用于新候选比较；依据授权约定从活动数据、原始证据库、缓存/索引与备份中删除或隔离，并重新校验数据集哈希与准入门槛。
- 不向 Provider 发送授权原件、评审身份、评审标签或个人偏好。候选模型只收到冻结任务输入及既定提示。

## 6. 最小交付包与当前状态

每个冻结评测版本需包含：

- `blind-eval.jsonl` 的 SHA-256、schema/准入协议/标注手册版本；标注口径见 `datasets/ai-evaluation/annotation-handbook-v1.0.md`。
- 去重与冻结策略版本/hash、语义族审查与 split 分配记录；策略见 `datasets/ai-evaluation/dataset-freeze-policy-v1.0.md`。
- 每条记录对应的 `source_ref`、授权状态、受控证据引用与证据哈希。
- 两份独立原始评审提交引用、提交时间/包哈希、盲包版本；必要时第三方裁定证据。
- 身份映射密封库引用及独立性核验人的受控角色引用、核验结论/日期。
- `blind-validate --training` 输出及其与 gold 字节哈希的绑定。
- 例外、拒绝、撤回和删除记录。

例外清单本身仅保存 `exception_ref`、受控 `category`（授权、隐私、评审独立性、裁定、保留、撤回、数据完整性或其他）、`status`（open/resolved/rejected/withdrawn）、记录时间、负责角色，以及成对出现的可选 vault 证据引用和 SHA-256；不得在 `exceptions` 中填写自由文本、评审意见、原始样本、个人身份或授权正文。需要说明原因时，将材料保存在受控证据库，并只引用其不透明 ID 与 SHA-256。签名结构可由受控系统按其签名方案保存，但本地工具不会验证签名真实性。

当前没有真实数据集和受控证据材料。本规程与模板只为将来接收定义操作合同；当前授权、评审独立性和阶段 0 均为 **not verified**。

### 执行顺序与停止点

1. 先确认来源权利和职责分离，再建立 v3 样本集与来源登记；没有授权原件或用途不覆盖候选推理/人工评审的来源，停止接收该来源。
2. 在受控评审系统生成盲包、分别收集双评和必要裁定；身份映射、原始授权和答卷不放入普通 Git 路径。
3. 冻结样本字节、规则版本和 hash；运行 `source-register-validate`、`blind-evidence-validate`、`blind-validate --training`，再由独立角色人工完成真实性核验。工具绿灯仅证明记录结构，不能代替人工/外部核验。
4. 只有 A0.1 证据链全部通过后才启动 A0.2。启动前固定产品提示快照、候选模型精确版本、推理参数和目标硬件；云端候选还需单独明确调用授权和预算。若未批准云端调用，A0.2 仅可记录可执行的本地候选，不能悄悄改走云端。
