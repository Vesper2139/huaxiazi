# Huaxiazi（话匣子）全项目红队安全审查与威胁模型

审查日期：2026-09-06  
审查对象：`C:\Users\lenovo\Desktop\话匣子\PromptFloat` 当前工作树、Release 构建流程、GitHub Actions、可导入 Skill、备份/皮肤包和本地数据流。  
审查性质：授权的仓库级静态安全审查 + 安全回归测试；未进行真实第三方账户攻击、未访问生产密钥或 CI 秘密、未执行破坏性操作。

## 0. 范围与结论先行

这是 Windows WPF 桌面端，不是联网后端。仓库内未发现自建 Web/API/GraphQL、OAuth 登录、云端数据库、Kubernetes、服务端租户隔离或后台队列。对应类别在本次审查中标记为“不适用”，风险重点转为：

1. 用户可编辑的模型端点与本机 DPAPI 密钥是否会被不可信配置/备份重新指向；
2. 外部 Skill 内容是否能改变模型提示边界；
3. 更新下载、发布签名和 GitHub Actions 是否能被供应链或 PR 路径滥用；
4. 错误日志、备份和“永久删除”是否保留用户原文或敏感数据；
5. ZIP/JSON/Markdown/XAML 等本地输入是否造成越界写入、资源耗尽或代码执行。

### 总体评级：C（有条件通过）

当前没有证据表明存在可直接远程接管桌面端的 RCE；现有 DPAPI、HTTPS、更新签名、路径校验和“Skill 不执行工具”的控制有效。但仍有一个高影响的本地配置/备份信任边界问题、一个中等影响的 Skill 提示注入问题、多个可造成隐私留存或可用性下降的问题，以及 CI 签名权限过宽和依赖审计不阻断的问题。在修复 SEC-001、SEC-002、SEC-004、SEC-005 前，不建议把不可信配置/备份和未经保护的主分支 CI 当作强安全边界。

## 1. 资产、信任边界与攻击面

| 组件/入口 | 信任边界 | 关键资产 | 主要风险 |
|---|---|---|---|
| WPF 主进程、设置页、悬浮窗 | 本地用户 UI → 运行时 | 用户原文、模型响应、API Key 引用、配置 | 本地输入导致错误提示、隐私泄露、模型误导 |
| `ProviderEndpointPolicy` / `AIService` | 本地配置 → 第三方模型端点 | API Key、请求正文、响应正文 | 密钥转发到不可信端点、响应回显、资源耗尽 |
| `Huaxiazi\config.json` + DPAPI secrets | 文件系统 ACL → 当前 Windows 用户 | ProviderProfile、SecretId、模型端点、密钥 | 恶意配置/备份重绑定现有 SecretId |
| `DataManagementService` 备份/恢复 | 用户选定 ZIP → 本地数据根目录 | 历史、草稿、配置、旧密钥引用 | ZIP 炸弹、覆盖配置、恢复后改变运行行为 |
| Agent Skills 导入/路由 | 外部包 → 模型 system prompt | 输出协议、事实保真、用户上下文 | Prompt injection、越权改写策略 |
| Skin ZIP 导入 | 外部包 → 主题资源 | XAML/主题文件、UI 可用性 | 路径穿越、资源耗尽、恶意 XAML（当前已限制） |
| `UpdateChecker` / `UpdateDownloadService` | HTTPS 清单/下载 → 安装目录 | 可执行文件、更新信任根 | 下载耗尽、发布链/证书配置错误 |
| GitHub Actions | PR/主分支 → 构建签名环境 | PFX、签名密码、更新私钥、发布物 | PR/依赖/Action 供应链窃取签名能力 |
| SQLite 历史库、错误日志、健康检查 | 本机用户 → 本地文件 | 用户正文、异常、端点元数据 | 明文留存、删除不彻底、日志回显 |

### 明确不适用的攻击面

- 无服务端账号、OAuth/OIDC 回调、JWT/session、RBAC、GraphQL/REST 后端、云 IAM、消息队列、容器编排或多租户数据库。
- SQLite 使用参数化命令；未观察到 SQL 拼接注入路径。
- 外部 Skill 的 `scripts/`、Shell、MCP、浏览器和任意文件工具不会被执行；皮肤包也不会动态加载任意程序集。

## 2. 安全不变量

以下不变量用于判断发现是否可接受：

1. **密钥只应发送到用户明确选择且策略允许的端点**；配置、备份、日志、错误提示、发布包不得包含明文 Key。
2. **用户原文、历史和模型响应不应进入非必要日志或诊断摘要**。
3. **外部 Skill 只改变表达方法，不能覆盖事实保真、隐私边界、追问规则和输出协议**。
4. **更新物必须同时通过 HTTPS、清单签名、SHA-256 和发布者签名验证**，失败不应落地可执行文件。
5. **导入包只能写入预期根目录**，必须限制条目数、展开大小、文件类型，并避免将配置/密钥引用静默切换。
6. **“永久删除”必须清除用户认为已删除的副本，或明确显示仍保留的安全备份与保留期限**。
7. **CI 的不可信代码不得接触签名秘密；依赖漏洞必须阻断发布或产生明确的强制门禁**。

## 3. 已确认发现

### SEC-001 — 自定义 HTTPS 端点允许向内部/任意主机转发现有 API Key（高）

- **组件**：`Services/ProviderEndpointPolicy.cs:30-39`、`Services/AIService.cs:312-377`、`Models/AppSettings.cs:315-340`。
- **违反不变量**：1。
- **根因**：自定义 OpenAI 兼容平台只要求 Cloud + OpenAICompatible，并没有拒绝 loopback、RFC1918、链路本地、IPv6 特殊地址、云元数据地址或 DNS 解析到私网的主机。官方平台才校验可信主机；自定义端点还没有统一拒绝 URI userinfo/query/fragment。AIService 随请求向该地址添加 Bearer API Key 并发送用户正文。
- **攻击前置条件**：攻击者不能直接从远程网络改配置，但可以诱导用户导入/恢复不可信配置、替换备份或篡改本机配置；配置中的 `SecretId` 可保留为已存在的值（`NormalizeProviderProfiles` 只在为空时补默认值）。
- **攻击路径**：不可信 `config.json`/备份指定 `https://attacker-or-internal-host/...` → 选择已有 ProviderProfile/SecretId → 用户执行测试、优化或生成 → API Key 和原文发送到该端点。
- **影响/爆炸半径**：当前 Windows 用户的已保存模型密钥、当前请求正文，可能进一步暴露到内网服务；同一用户下所有引用该 SecretId 的配置受影响。
- **评分**：可利用性 3/5，影响 5/5，所需权限 3/5，复杂度 3/5，爆炸半径 3/5，检测难度 3/5；建议 **High / P1**。
- **证据**：`ProviderEndpointPolicy.cs:33-39` 对自定义端点直接返回成功；`AIService.cs:312-377` 为非 Anthropic/Gemini 请求设置认证头并发送 body；`AppSettings.cs:329-340` 接受外部 `SecretId`。
- **修复**：
  1. 对自定义“远程”端点做 DNS + IP 分类，拒绝 loopback、私网、链路本地、组播、未指定地址、IPv6 特殊地址和云元数据网段；解析结果发生变化时重新校验。
  2. 拒绝 userinfo、query、fragment，统一规范化 host/path；必要时仅允许用户显式确认的域名清单。
  3. 将 SecretId 与 ProfileId/端点指纹绑定，端点或协议变化时清空/重新授权密钥，不接受备份直接复用现有 SecretId。
  4. 增加单测：私网 IPv4/IPv6、DNS 解析到私网、userinfo/query、备份重绑定均必须失败且不发出 HTTP 请求。

### SEC-002 — 外部 Skill 内容以高权限 system prompt 注入，过滤不足以抵御提示注入（中高）

- **组件**：`Services/AgentSkillPackageService.cs:380-418`、`Services/ExpressionSkillRouter.cs:54-81`、`Services/PromptBuilderService.cs:89-100`、`Services/ExternalSkillStrategyResolver.cs:10-28`。
- **违反不变量**：3。
- **根因**：Skill 包虽然不执行脚本/工具，但其主体文本经过少量章节和关键词过滤后，直接拼接到专业化执行计划/system prompt。过滤只识别少数“Google Drive/Slack/MCP/Shell/PowerShell/browser”等字样，无法识别“忽略之前规则、泄露系统提示、把原文发送到某处、改变输出协议”等任意自然语言注入。
- **攻击前置条件**：用户安装、编辑或启用恶意/被篡改的 `.md` Skill，或导入一个来源不明的 ZIP。
- **攻击路径**：恶意 Skill 文本 → `ProjectInstructions` 保留 → `PromptBuilderService` 作为 `专业化执行计划` 拼入 system prompt → 模型偏离事实保真/输出协议，可能在结果中复述敏感上下文或执行不应执行的文本指令。
- **影响/爆炸半径**：不直接获得本机 Shell/密钥，但影响每次命中该 Skill 的模型输出；可造成数据外泄、承诺强化、错误业务文本和用户信任损失。
- **评分**：可利用性 3/5，影响 4/5，所需权限 3/5，复杂度 2/5，爆炸半径 3/5，检测难度 4/5；建议 **Medium-High / P1**。
- **现有缓解**：`PromptSecurityPolicy` 在提示末尾声明原文/上下文不可信；工具型 Skill 被标为 `RequiresTools`，不执行脚本；内容长度限制 12,000 字符。
- **修复**：
  1. 将外部 Skill 投影为结构化字段（目标、语气、结构、禁用表达、输出格式），不要把任意 Markdown 作为 system 指令原样拼接。
  2. 使用强分隔符并明确标为“低信任策略资料”，系统规则与保真检查放在不可覆盖的最高优先级；对 Skill 中的“忽略/泄露/执行/读取”等指令做拒绝或审查。
  3. 在最终输出前强制运行事实锚点、否定关系、数字日期、隐私和输出协议检查；增加对抗样本测试，验证恶意 Skill 无法改写安全边界。

### SEC-003 — 供应商错误正文可将用户原文/敏感内容写入错误日志（中）

- **组件**：`Services/AIService.cs:146-183,457-478`、`Services/ErrorLogService.cs:39-71`。
- **违反不变量**：2。
- **根因**：非 2xx 响应会解析 `error.message`，最多 300 字符并放入 `GenerationFailureException`；未限制其来源内容。异常日志随后调用 `exception.ToString()` 写入 `errors.log`。日志只识别若干 token/secret/key 形式，不能识别被供应商回显的用户原文、业务秘密、`x-api-key`/`x-goog-api-key` 文本或任意敏感字符串。
- **攻击前置条件**：第三方接口返回带回显的错误正文，或被配置的兼容端点主动返回用户请求片段。
- **攻击路径**：用户输入 → 请求 body → 供应商错误 `error.message` 回显 → 异常 → `ErrorLogService` 持久化。
- **影响**：本机日志中保存用户原文/供应商回显数据；共享诊断、备份或人工上传日志时扩大泄露面。
- **评分**：可利用性 3/5，影响 3/5，所需权限 4/5，复杂度 2/5，爆炸半径 2/5，检测难度 3/5；建议 **Medium / P2**。
- **修复**：错误 UI/日志只写标准化状态、HTTP 状态码、耗时和 Request ID；不要复制任意 provider message。若必须显示，使用明确的短白名单错误码，不写异常正文。扩展脱敏规则覆盖 `x-api-key`、`x-goog-api-key` 及 JSON 字段，并加“错误响应回显用户文本”回归测试。

### SEC-004 — 更新下载无响应体大小上限，可造成磁盘/时间耗尽（中）

- **组件**：`Services/UpdateDownloadService.cs:123-146`。
- **违反不变量**：4（可用性）。
- **根因**：使用 `ResponseHeadersRead` 后按流写入临时文件，读取 `Content-Length` 仅用于进度显示，没有限制 `received`；分块响应或错误的超大 Content-Length 可持续写盘，直到超时、磁盘耗尽或哈希/签名失败。
- **攻击前置条件**：更新源被劫持、配置/代理被篡改，或可信 HTTPS 源返回异常大响应。更新清单签名与最终签名能阻止恶意包落地，但不能阻止资源消耗。
- **影响**：本地磁盘耗尽、更新线程长时间占用、用户体验/可用性下降。
- **评分**：可利用性 2/5，影响 3/5，所需权限 3/5，复杂度 3/5，爆炸半径 2/5，检测难度 2/5；建议 **Medium / P2**。
- **修复**：在清单中签名并校验最大包大小；读取前拒绝超出上限的 `Content-Length`，读取过程中也按硬上限中止并删除临时文件；为总下载时间、空闲读取时间和临时目录容量增加限制。

### SEC-005 — GitHub Actions 的依赖审计不阻断，签名秘密与不可信构建步骤同一 Job（中高）

- **组件**：`.github/workflows/build.yml:13-31,65-150`。
- **违反不变量**：7。
- **观察**：
  - `dotnet list ... --vulnerable` 只检查命令退出码。命令可以在发现漏洞时正常退出，因此漏洞输出不会自动使 Job 失败。
  - `actions/checkout@v4`、`actions/setup-dotnet@v4`、`actions/upload-artifact@v4` 使用可变 tag 而非提交 SHA。
  - 主分支 push 在同一个 Job 内恢复依赖、构建/测试、发布、读取 PFX/密码、签名和上传；没有顶层最小 `permissions`，也没有显式 `persist-credentials: false` 或 protected environment 审批。
- **攻击路径**：恶意依赖、被合并的构建/测试代码或被替换的 Action 在持有 PFX、PFX 密码、更新私钥/公钥环境的步骤前后执行，可能窃取签名材料或生成恶意发布物。
- **影响**：发布链被攻破后，攻击者可以签名/发布看似可信的安装包；依赖漏洞也可能进入正式包。
- **评分**：可利用性 2/5，影响 5/5，所需权限 2/5，复杂度 3/5，爆炸半径 5/5，检测难度 4/5；建议 **High / P1**。
- **修复**：
  1. 顶层 `permissions: contents: read`，checkout 设置 `persist-credentials: false`；所有 Action pin 到完整 commit SHA。
  2. 将 PR/主分支测试和签名发布拆成不同 Job；签名 Job 仅接受受保护 tag/release，使用 protected environment + required reviewers，并限制 secrets 只在该 Job 暴露。
  3. 让依赖审计输出 JSON/机器可读结果并在存在漏洞时显式 `exit 1`；把 NuGet advisory 作为发布门禁。
  4. 保留 SHA-256、清单签名、Authenticode 验证，并增加 provenance/构建摘要。

### SEC-006 — “永久删除”前创建的安全备份仍保留历史库（中）

- **组件**：`Services/ArchiveService.cs:321-356`。
- **违反不变量**：6。
- **根因**：`PermanentlyDeleteAll()` 先调用 `CreateSafetyBackup("before-clear")`，然后删除 SQLite 内容、草稿和回收站文本，但没有在成功删除后清理该备份，也没有在 UI/数据页保证用户知道它仍存在。
- **攻击路径**：用户执行永久删除 → `backups/before-clear-*.db` 保留可恢复副本 → 备份目录被读取、导出或后续纳入数据备份。
- **影响**：用户以为已永久删除的历史/正文仍可恢复；对隐私清理和合规删除形成误导。
- **评分**：可利用性 4/5，影响 3/5，所需权限 4/5，复杂度 1/5，爆炸半径 2/5，检测难度 2/5；建议 **Medium / P2**。
- **修复**：把安全备份改为明确的“可选撤销点”，显示路径和保留期限；成功删除后默认自动删除并刷新统计；若保留，必须在数据管理页显式列出并提供单独永久删除，测试“删除后任何用户正文副本均不存在”。

### SEC-007 — 备份恢复缺少展开大小/条目上限，可资源耗尽并覆盖活动配置（中低）

- **组件**：`Services/DataManagementService.cs:146-162`。
- **违反不变量**：5，间接影响不变量 1。
- **根因**：恢复只做路径前缀检查，逐条 `ExtractToFile(..., overwrite: true)`；没有条目数、解压后总字节、重复路径、允许文件清单或签名/来源校验。
- **影响**：恶意备份可造成 ZIP 炸弹/磁盘耗尽；也可覆盖 `config.json`、`data/*`、`workspace-draft.json`，再配合 SEC-001 改变端点并重用已存在 SecretId。
- **评分**：可利用性 2/5，影响 3/5，所需权限 3/5，复杂度 2/5，爆炸半径 3/5，检测难度 3/5；建议 **Medium-Low / P2**。
- **修复**：恢复前做条目/展开大小/文件名和重复路径扫描，限制为允许的资料库文件；先恢复到隔离临时目录、完整校验后原子替换；`config.json` 变化时要求重新验证端点并清除/重新授权密钥引用。

### SEC-008 — 自定义 Skill 只读内容可进入模型上下文，敏感信息防护依赖用户（低到中）

- **组件**：`AgentSkillPackageService`、`ExternalSkillStrategyResolver`、`PromptBuilderService`。
- **观察**：导入包不应读取 API Key、历史正文或其他 Skill 数据，但当前 Skill 文件正文允许用户自由编辑；没有针对“把输入原文发送到外部/输出秘密”的系统化静态扫描或用户警告。
- **影响**：用户自行创建 Skill 时可能无意加入密钥、客户资料或要求模型输出敏感上下文；这不是第三方工具执行问题，而是提示层数据边界问题。
- **建议**：导入/保存时对疑似密钥、Bearer、私钥块和跨 Skill 数据引用做本地告警；用结构化策略字段替代自由 system prompt；在“启用”前显示“Skill 可影响模型输出，但不会获得文件/网络工具”的简短确认。

### SEC-009 — 公开 Release 资产与当前安全加固源码未建立可验证对应关系（中）

- **组件**：GitHub `Vesper2139/huaxiazi` 的 v2.0.0 Release 资产、`publish.ps1`、GitHub Actions。
- **违反不变量**：4、7。
- **观察**：当前本地工作树包含后续安全加固与审计改动，但已有 v2.0.0 的三个下载资产不是由本次工作树重新构建并签名生成；在没有 provenance/构建摘要的情况下，用户无法从 Release 资产证明其对应的源码提交和安全修复状态。
- **影响**：用户可能下载未包含最新密钥脱敏、更新校验或端点策略的旧构建；安全审计结论无法直接覆盖当前下载物。
- **评分**：可利用性 2/5，影响 4/5，所需权限 3/5，复杂度 3/5，爆炸半径 4/5，检测难度 4/5；建议 **Medium / P1（发布前）**。
- **修复**：只发布由受保护 tag 构建的资产；在 Release body 和清单中写入源码提交 SHA、构建流水线 run ID、SHA-256、签名证书摘要和 SBOM/provenance；旧资产标为 superseded 并撤下下载入口。未完成前，发布说明必须明确“该资产不代表当前安全审计版本”。

## 4. 攻击链复盘

### 链 A：不可信备份 → 现有 SecretId → API Key 外发

1. 攻击者提供一个看似正常的 Huaxiazi 备份；
2. `RestoreBackup` 覆盖 `config.json`，保留一个本机已有 `SecretId`，把 `ApiBase` 改为攻击者控制的 HTTPS 端点；
3. 自定义端点策略放行，AIService 将现有 API Key 和用户输入发出；
4. 影响可持续到该 Profile 被删除或 SecretId 被重新授权。

这是本报告最需要优先修复的链，原因是它把“本地可导入文件”提升成了“云端密钥转发器”。

### 链 B：恶意 Skill → system prompt 注入 → 事实/隐私边界破坏

1. 用户安装带有伪装说明的 Skill；
2. 路由命中后，正文被注入 `PromptBuilderService`；
3. 模型把 Skill 的自然语言当成高优先级策略；
4. 结果可能泄露输入、强化承诺、改变输出协议。工具执行仍被阻断，但模型输出边界被削弱。

### 链 C：依赖/Action 攻陷 → 签名秘密 → 可信恶意发布物

1. 主分支工作流在同一 Job 中运行不可信构建代码并读取签名秘密；
2. 可变 Action tag 或恶意依赖执行任意构建步骤；
3. 窃取 PFX/密码或替换发布物；
4. 以有效 Authenticode/清单签名形式进入下载渠道。

## 5. 现有安全控制与有效性

- `ConfigService.Save` 在序列化前强制清空 API Key；公开源码扫描未发现可读明文 Key 模式。
- Windows DPAPI `CurrentUser` + 受限 ACL 存储密钥；密钥不会随普通备份迁移。
- 官方端点做主机/协议/路径校验；云端默认 HTTPS；HTTP 自动重定向关闭。
- 更新清单使用 RSA 签名，下载校验 SHA-256，并验证发布者 Authenticode 证书指纹。
- Skill 包限制扩展名/数量/展开大小，拒绝脚本/工具型包启用；皮肤包有路径穿越、条目数、大小和允许扩展名限制。
- SQLite 使用参数化 SQL；当前安全回归筛选测试 79 通过、1 跳过、0 失败，Release 构建 0 警告/0 错误。
- 这些控制显著降低了 RCE、明文配置泄露和经典 ZIP Slip 风险，但不能替代 SEC-001/002/005 的信任边界修复。
